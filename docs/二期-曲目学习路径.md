## 0. 一句话

把古典钢琴「技术为曲目服务 + 逆向设计」的教学法搬到流行曲上：**App 提供能力骨架，课程与曲目以数据包形式接入；一首曲目拆成技能需求、按技能图谱评级，用户可选「按部就班」或「先选曲」两条路径学习，并通过 3D 示范演奏获得"看示范"的闭环反馈。**

但 v0.3 必须先说清楚一个边界：**识谱主线 L1–L3 已有完整课程与通关测试（L1/L2 生成器 + L3 四节和弦课 + 过关），乐理侧另有 L3 预备 9 节与 L4 预备 2 节；L4–L6 仍只有词汇/规则与零散预备课，没有完整课程**。当前 `Score` 也只能表达单声部、无反复/速度变化的乐谱（**跨小节连音线与弱起小节已在 P1.5 补齐**）。因此二期的正确目标不是"任意流行曲都能弹"，而是：

> **先用一个受控曲库把「拆解 → 评级 → 补短板 → 示范 → 跟弹」跑通，再按词汇表扩展节奏逐批放量。**

## 1. 背景、现状与边界

### 1.1 从 MVP 到二期：现状校正

MVP 已解决「先识谱、再视奏」的主线：L1–L2 课程 + 生成器 + 指法引擎 + MIDI 识别 + 复盘。二期在 MVP 之上增加「曲目学习」板块，回答三个 MVP 刻意回避的问题：

1. 学会了音和节奏，怎么弹一首真正的、自己喜欢的歌？
2. 如何让"练基础"和"弹喜欢的歌"互相成全，而不是互相抢时间？
3. 自学成人没有老师示范，怎么"看见"标准手型和指法？

但设计不能建立在"MVP 已有 L1–L6 课程"的假设上。当前真实状态：

| 能力 | 当前状态 | 对二期的影响 |
|---|---|---|

| 平台 | 主项目 Web（Vue + Vite）；demo 独立 Three.js | 二期默认 Web-first，Flutter 另议 |

### 1.2 本期曲库边界（新增，P1 的硬约束）

当前词汇表（`src/domain/vocabulary.ts`、`allowed.ts`）实际支持：

- **调号**：C / F / G / D / Bb 大调；**没有小调**。
- **拍号**：4/4、3/4；**没有 6/8、三连音、自由速度**。
- **和弦**：只允许 C–E–G、F–A–C、G–B–D 三个原位大三和弦；**没有小三和弦、转位、七和弦**。
- **节奏**：全/二分/四分/八分/附点/十六分；**支持跨小节连音线（`NoteEvent.tie`）与弱起小节（`Score.pickup`）**；**没有反复记号**。
- **声部**：每只手一个 `pitches[]`，**没有多声部/内声部**。
- **结构**：`Score` 没有反复、段落、速度地图、力度、踏板。

这意味着：**大量流行曲在 P1 根本无法被当前 `Score` 表达。** 例如：

- 小调歌曲（《River Flows in You》等）→ 调号/和弦不支持。
- 4/4 切分流行歌 → 切分可检测，跨小节延音与弱起小节已能表达；小节内切分仍只能靠视觉提示。
- 有前奏/反复/桥段的完整歌 → 只能手工截成"主歌 8 小节"的练习版。

**P1 的曲库决策（推荐默认）**：

1. **只做三类内容**：公版改编（public domain）、原创教学曲、明确授权的少量曲目。
2. **只做当前词汇表能表达的编配**：C/F/G/D/Bb 大调、4/4 或 3/4、单声部旋律 + 根音/五音/三和弦/简单分解和弦。
3. **一首歌先做 8–16 小节**，不做完整 3 分钟；完整版留到 `Score` v2。
4. **不承诺"任意流行曲"**；产品文案改为"每周上新一首能弹的简化版"。

**词汇表扩展顺序（P1.5 之后，按投入产出排序）**：

| 优先级 | 扩展 | 为什么先做 | 影响 |
|---|---|---|---|
| P1.5 | 跨小节连线 | 流行曲几乎必用；没有它连主歌都切不干净 | ✅ 已落地：`NoteEvent.tie` + 派生合并 + `isAllowed` + 渲染 + MusicXML 导入 |
| P1.5 | 弱起小节 | 大量民谣/流行曲从弱拍进旋律，没有它第一小节拍数就算错 | ✅ 已落地：`Score.pickup` + `isAllowed` + 渲染缩窄 + 网格偏移 + 导入器 |
| P1.5 | 反复记号 | 可先手工展开成线性小节，优先级低于弱起 | `Score` v3 + 渲染 |
| P1.5 | 小调调号 + 小三和弦 | 大量流行/影视曲是小调 | 词汇表/和弦表/指法/评级 |
| P2 | 6/8、三连音 | 抒情歌常见 | 节拍/时值/评测对齐 |
| P2 | 和弦转位、七和弦 | 流行和声色彩 | 和弦识别/编配/课程 |
| P3 | 多声部、踏板、力度/速度地图 | 完整演奏表现 | `Score` v3 + demo |

> **一句话：P1 的曲库不是"流行曲库"，是"当前词汇表能承载的教学曲库"。** 这个边界必须在 PRD 和商店文案里同步，避免"什么歌都能弹"的预期落差。

### 1.3 借鉴古典教学法（可自动化部分）

| 古典教学法 | 对应到本设计 |
|---|---|
| 五指位置 → 音阶 → 琶音 → 和弦逐调扩张 | **技能图谱**（§3），MVP 词汇表图化 |
| 练习曲 = 针对单一技术点的迷你曲 | 沿用 MVP 识谱课「一课一个新点、5 分钟内」 |
| 分级曲目 = 每级定义明确技能集 | **难度评级**（§5），曲目 = 技能包 |
| 技术为曲目服务 + 逆向设计 | **先选曲路径**（§7.2） |
| 老师现场示范 | **示范演奏层**（§8，piano-buddy-demo） |

### 1.4 两条学习路径

- **路径 A · 按部就班**：从基础逐级提升（技能图谱自下而上全量），每一级都有「此刻就能弹」的曲目作里程碑，基础扎实、曲库随等级自然扩大。
- **路径 B · 先选曲**：先选想弹的歌（按拆解结果评级）→ 生成"补短板"技能清单 → 逐个学练 → 快速弹出喜欢的歌，成就感驱动。

两者是**同一张技能图谱的两种遍历顺序**，进度互通（见 §7.3）。

## 2. 核心架构：能力骨架 + 内容数据包

### 2.1 分层原则

**引擎与内容解耦。** App 只交付"能力"与"骨架"，课程、曲目、编配全部作为**数据包**加载。这条原则贯穿二期及以后所有板块。

```
┌─────────────────────────────────────────────┐
│  能力骨架（App 本体，随版本发布）              │
│  指法引擎 · 识谱/视奏 · MIDI 识别 · 难度评级   │
│  示范演奏层 · 进度跟踪 · 复盘 · 谱面渲染        │
├─────────────────────────────────────────────┤
│  数据包（独立分发，热加载）                    │
│  课程包（技能） · 曲目包（歌曲+编配） · 练习包   │
└─────────────────────────────────────────────┘
```

### 2.2 为什么用数据包

| 收益 | 说明 |
|---|---|
| **版权隔离** | 曲目独立分发：平台只发无版权包（公版曲、原创练习）；授权曲目走独立渠道或用户自行导入 MIDI。App 本体零侵权风险 |
| **内容可运营** | 上新曲/新课程不发版，像 DLC 增量发布，匹配成人"想弹新歌"诉求 |
| **UGC 扩展** | 用户导入 MIDI → 拆解引擎生成编配 → 打包分享，复用拆解/评级能力 |
| **按需加载** | GLB 手模型、曲库、音频采样等大文件按包懒加载，控制首包体积 |

### 2.4 平台与集成边界（新增）

**默认决策：二期 Web-first，不把三件事混在一起。**

1. **主项目**：Vue + Vite，负责课程、曲目列表、评级、进度、评测、谱面。
2. **示范层**：独立 `piano-buddy-demo`，负责 Three.js 手部动画；通过 **Motion IR** 接收事件，不直接读主项目的 `Score`。
3. **曲目包**：JSON/资源目录，先本地加载；在线分发/签名留到 P3。

集成方式三选一：

| 方案 | 做法 | 优点 | 缺点 | 建议 |
|---|---|---|---|---|
| A. 复制适配层 | demo 内新增 `motionAdapter.ts`，把 `MotionNote[]` 转成 demo 的 `NoteEvent` | 最快，1–2 天；不引入构建耦合 | 两份代码需同步 | **P1 先用 A** |
| B. npm workspace 包 | 抽 `@piano-buddy/motion`，主项目/demo 共用 | 类型单一来源 | 需要 monorepo/构建调整 | P2 再做 |
| C. iframe + postMessage | demo 作为独立页面嵌入，传 Motion JSON | 隔离最好；可单独部署 | 调试/时钟同步更麻烦 | 若 demo 要独立上线再选 |

**明确不做**：P1 不把 three.js 打进主包（当前主包已 1.15 MB / gzip 372 KB），也不把课程/评测逻辑搬进 demo。

### 2.5 作者工具与内容预算（新增）

**没有作者管线，曲库就是手工 JSON 堆出来的，无法持续。** P0.5 先做最小管线：

```
MusicXML (.musicxml) ──► 规范化 ──► Score JSON ──► 指法引擎 ──► validateSongContent ──► 曲目包
        │                    │                          │
        └─ 单声部/简单和弦    └─ 拍号/调号/时值映射       └─ finger 1..5 硬校验
MIDI（P3）──────────────────┘
```

**已落地（2026-10-28）**：`src/repertoire/musicxml.ts` + `npm run import:musicxml`。

- **解析器自带**：没有引第三方 XML 库（主项目只有 3 个运行期依赖），`parseXml()` 支持元素/属性/文本/实体/注释/CDATA，结构错误带字符偏移报错。
- **支持范围**（与 `Score` 当前能力一一对应）：`score-partwise`；单行谱或钢琴大谱表（`<staves>2</staves>` 或两个 `<part>`）；`divisions`/`<backup>`/`<forward>`；4/4 与 3/4；C/F/G/D/♭B 大调；全到十六分音符与附点；`<chord/>` 和弦；`<tie>`（小节内与跨小节都支持，保留成 `tie: start/stop/continue` 链，不再合并成单个长音）；**弱起小节**（首小节不满拍即按 `Score.pickup` 导入，不补休止符，两手拍数必须一致）。
- **超纲一律报错，不静默降级**：`score-timewise`、6/8 及其它复合拍、两个升降号以上的调号、32 分音符、三连音（`<time-modification>`）、`alter` 超出 ±1、一行谱多声部（可用 `--voice` 指定保留哪一声部）、两手首小节拍数不一致（一手弱起一手满拍说明小节线没对齐）。理由：这些「取近似值听感就变了」，作者必须知道。
- **连音线必须接得上**：`start` 后面要跟同音高的 `stop`/`continue`，中间不能隔别的音或被休止符打断；导出的谱会再过一遍 `tieErrors`，内容 QA 把断线算成错误（跟弹会在断口处要求重新击键，听起来就是错的）。
- **能无损修的会修并说明**：小节缺拍补休止符、两只手小节数不齐的补空小节、装饰音跳过。
- **两个评级是刻意的**：转换后先按**音高**评级（谱面本身要求什么，用它写 manifest），再补指法按**指法**评级（CI 的 `validate:content` 用这个）。求解器只看局部连贯，可能把一段 C 手位旋律判成 D-shift/扩张，把 L3 抬成 L5；脚本会把两个数都打出来并提示「补出来的指法只是起点，需要人工校对」——这也是内容预算里「指法 0.5 天/版」的由来。

```bash
npm run import:musicxml -- song.musicxml                       # 看报告 + manifest 建议字段
npm run import:musicxml -- song.musicxml --out content/song.x/content/score.json --id score.song.x --bpm 96
npm run import:musicxml -- song.musicxml --manifest content/song.x/manifest.json   # 转换 + 内容 QA
```

- **P1 输入格式只承诺 MusicXML**：MuseScore 导出稳定、可版本控制；MIDI 的时值/声部/踏板太脏，留到 P3。`.mxl`（压缩包）请先在 MuseScore 另存为 `.musicxml`。
- **手工 JSON 仍是兜底**：小曲/原创练习可以直接写 `score.json`，但必须过 `validateSongContent`。

#### 弱起小节（2026-10-28 落地）

弱起最常见的写法是「首小节不满一个整小节」：4/4 的曲子从第 4 拍进旋律，3/4 的从第 3 拍进。落地口径如下，改这块代码时别绕开：

- **记成「首小节有几拍」**：`Score.pickup = 1` 表示首小节只有 1 拍，`0 < pickup < meter.beats` 且是十六分音符的整数倍。记「缺几拍」会让语义随拍号漂移。
- **首小节时值必须与 pickup 一致**：`domain/pickup.ts` 的 `pickupErrors()` 是唯一判据，`isAllowed` 与 `validateSongContent`（内容 QA）共用——否则「声明弱起」只是个标签。
- **事件流不动**：弱起的第一个音仍是从第 0 拍起算的第 0 拍。会变的是**小节边界**，所以小节号一律走 `measureBeatStarts()` / `barAtBeat()`，不要 `beat / meter.beats` 硬除。跟弹的 `RhythmPlan` 带上 `measureStarts` + `pickupBeats`，网格小节线与拍号标签（4/4 弱起标第 4 拍）都读它，报错定位也不会偏到隔壁小节。
- **渲染分两条路**：单手谱面（EasyScore voice 是 STRICT）在首小节**前面**补休止符，音符才落在小节末尾；双手大谱表不补休止符，改成按拍数**缩窄首小节**（`120 + 240 × pickup/beats`，满拍时正好回到 360）。若把休止符补在后面，弱起会被画成「第一拍起音」。
- **切片只保留第一段的弱起**：从中间切出来的段落首小节是整小节，继续带着 `pickup` 会让 `isAllowed` 与网格都算错，`sliceScore` 会清掉。
- **导入器自动识别**：首小节不满拍即按 `pickup` 导入并在报告里说一声，不再报「暂不支持」；但两只手首小节拍数必须一致（一手短一手满说明小节线没对齐，硬导进来「第 2 小节」在两只手上会指向不同位置）。
- **端到端样本**：原创《晨歌》（`content/song.morning-song.l5`）是首小节 1 拍、第 6–7 小节还有一条跨小节延音的 L5 编配，`scripts/verify-pickup.mjs` 用它核对前置休止符、首小节缩窄、网格第 4 拍与真实页面。- **内容预算（建议按 1 人内容 + 0.5 人工程估算）**：

| 工作 | 单位成本 | P0.5（3 首 × 3 编配） |
|---|---|---|
| 选曲/版权确认 | 0.5 天/首 | 1.5 天 |
| 编配（L2/L3/L4 各一版） | 0.5–1 天/版 | 4.5–9 天 |
| 指法 + 内容 QA | 0.5 天/版 | 4.5 天 |
| 示范适配/播放控制 | 3–5 天 | 3–5 天 |
| 合计 | — | **约 3–4 周（1 人）** |

> 如果只做 1 首歌 × 3 编配，2 周可以跑通纵向切片；3 首歌是"能看出内容管线是否可复制"的最小批量。

### 2.6 课程缺口（新增，路径 A 的前置）

当前 `lessonProgress.ts` 只有 L1/L2 的课程序列；`skillGraph.ts` 已经声明到 L6，但**没有 L4–L6 课程**。L3 已在 2026-10 补了 5 节预备课（`src/practice/l3Lessons.ts` + `src/ui/L3PrepView.vue`），覆盖三和弦、临时升降、双音音程、和弦连接和综合小测；它解决的是"曲库页 L3 缺口有入口"，不是完整的 L3 识谱/视奏课。

两条可选路线：

| 路线 | 做法 | 成本 | 风险 |
|---|---|---|---|
| A1. 先补课程 | 每级 5–6 节微课（一课一个技能点）+ 过关测试 | 20–24 节，约 6–8 周 | 内容工作量大，但路径 A 完整 |
| A2. 先做路径 B | L3–L6 只做"补短板微练习"，不承诺完整课程 | 2–3 周 | 路径 A 文案必须改成"L2 后转为选曲模式" |
| A3. 混合 | L3 先补 5 节（三和弦/临时升降/和弦连接），L4–L6 用曲目补 | 3–4 周 | 推荐 P1 采用；L4+ 后续补 |

**建议 P1 采用 A3**：先把 L3 的三和弦/临时升降/和弦连接补成 5 节微课，让路径 A 能从 L2 走到 L3 里程碑；L4–L6 在 P2 补。

## 3. 技能图谱（词汇表图化）

### 3.1 定义

技能图谱是把 MVP 的 L1–L6 词汇表升级为**带前置关系的 DAG**。每个技能节点：

```
Skill {
  id: string          // 稳定标识，数据包据此声明依赖
  name: string        // 中文名
  level: 1..6         // 所属 MVP 档位
  prereq: string[]    // 前置技能 id
}
```

用户掌握状态**不放在节点上**，而是放在账本里（§7.3）：

```
SkillMastery {
  skillId: string
  hand: RH | LH | both | none
  state: locked | learning | passed
  bpm?: number
  confidence: number       // 0..1
  masteredAt?: number
  lastPracticedAt?: number
}
```

### 3.2 节点清单（与代码同步）

| 层 | 技能 id | 名称 | 档 | 代码是否可自动识别 |
|---|---|---|---|---|
| 基础 | `clef.treble` / `clef.bass` | 高/低音谱 | L1 | ✅ 按手 |
| 基础 | `pos.five` | 五指位置 | L1 | ✅ 基础要求 |
| 基础 | `rhythm.quarter` | 四分/二分/全音符 | L1 | ✅ |
| 调性 | `key.c` | C 大调 | L1 | ✅ |
| 调性 | `key.one-flat` / `key.one-sharp` | 一个降/升号 | L2 | ✅ |
| 调性 | `key.two-acc` | 两个升降号 | L4 | ✅ |
| 调性 | `key.accidental` | 临时升降号 | L3 | ✅ |
| 双手 | `hands.both` | 双手合奏 | L2 | ✅ 双手都有音 |
| 双手 | `hands.alternate` / `hands.together` | 双手交替 / 同拍 | L2 | ✅ 按发声音拍点 |
| 节奏 | `rhythm.eighth` | 八分音符 | L2 | ✅ |
| 节奏 | `rhythm.dotted` | 附点节奏 | L5 | ✅（按最复杂时值） |
| 节奏 | `rhythm.syncopation` | 切分节奏 | L5 | ⚠️ 启发式（半拍起、≥1 拍） |
| 节奏 | `rhythm.sixteenth` | 十六分音符 | L6 | ✅ |
| 和声 | `chord.interval` / `chord.triad` | 双音 / 三和弦 | L3 | ✅ 按同时发声音数 |
| 和声 | `chord.progression` | 和弦连接 | L3 | ✅ 不同三和弦 ≥2 |
| 和声 | `chord.inversion` / `chord.seventh` | 转位 / 七和弦 | L4/L5 | ❌ 当前 `Score` 不区分转位；七和弦可数音数但和弦表不支持 |
| 手位 | `pos.shift` | 手位平移 | L2 | ✅ 优先用指法；≥2 个显著手位（单手位覆盖 ≥3 音或 10%） |
| 手位 | `pos.expand` | 两端扩张 | L4 | ✅ 优先用指法；无指法时按音高 |
| 手位 | `pos.leap` | 六度/八度跳进 | L6 | ✅ 相邻发声事件取最近声部距离 ≥8 半音；和弦换位不算跨声部跳进 |
| 织体 | `texture.broken` | 分解和弦伴奏 | L4 | ⚠️ 启发式（低音手、两小节重复、三和弦音级） |
| 织体 | `texture.comp` | 柱式/半分解伴奏 | L4 | ❌ 暂不自动识别，manifest 声明 |
| 踏板 | `pedal.sustain` | 延音踏板 | L4 | ❌ `Score` 无踏板，manifest 声明 |

> **代码位置**：`src/repertoire/skillGraph.ts` 的 `SKILLS` 是唯一来源；新增节点必须同步 `test/repertoire.test.ts`。

### 3.3 图谱的两个用途

1. **驱动学习路径**：路径 A 按拓扑序推进；路径 B 只取"目标曲目 → 缺的节点"子图。
2. **声明数据包依赖**：每个数据包在 manifest 里声明它需要的技能 id 集合，加载器据此判定"当前用户能否学/弹"，并生成补短板清单。

### 3.4 粒度原则（新增）

技能节点不是越细越好。当前采用四条原则：

1. **可独立教学**：一个节点对应一节 5 分钟微课或一个可单独练习的动作。
2. **可独立验证**：能用一条练习/测试判断"会不会"，而不是靠主观感觉。
3. **可迁移**：在 C 手位学会的三和弦，换到 F 手位仍算同一技能；调号/手位另有节点。
4. **按手拆分**：`clef.treble` 只属于右手，`clef.bass` 只属于左手，`pos.*` 双手各自记录；`rhythm.*` / `key.*` / `pedal.*` 与手无关。

**不做**：不为每首歌建节点，不为每个速度建节点，不为每个调建节点。速度记录在账本的 `bpm`，调记录在 `key.*`。

### 3.5 拆解启发式的边界（新增）

`requiredSkillsForScore` 不是"音乐理解"，是**基于当前 `Score` 的启发式**。当前可靠/不可靠的边界：

| 判定 | 可靠性 | 说明 |
|---|---|---|
| 谱号、拍号、调号、时值、同时发声音数 | 高 | 直接读字段 |
| 双手交替/同拍 | 高 | 按发声音的拍点集合 |
| 切分 | 中 | 只识别"半拍起、≥1 拍"的典型切分；**跨小节延音现在能表达，但切分检测本身还不把它算进去** |
| 分解和弦 | 中 | 只识别低音手、连续单音、两小节重复、三和弦音级；柱式/半分解不识别 |
| 手位平移/扩张 | 中高 | **有指法时按指法判定**；8 小节曲里一个完整和弦（3 音）就可算换位，无指法时 C→D 平移可能被误判为扩张 |
| 和弦转位/七和弦 | 低 | 当前 `Score` 没有转位/和弦标记，只能数音数 |
| 段落重复/学习成本 | 无 | `Score` 没有反复/段落；`repeat` 只能由 manifest 声明 |

因此：**曲目包必须带指法（finger 1..5）**；`validateSongContent` 会把缺失指法/`finger=0` 当错误。无指法的乐谱只能用于预览，不能进曲库。

## 4. 流行曲拆解引擎

### 4.1 为什么流行曲更可拆

流行曲是 loop 化、段落重复、和弦套路化（I–V–vi–IV）、伴奏型有限的。一首 3 分钟的歌，拆出来往往只有 4~6 个"块"。拆解输出的是**技能需求清单**，不是整首歌的逐音教学。

### 4.2 拆解维度

| 维度 | 拆出什么 | 映射到技能 | 当前状态 |
|---|---|---|---|
| 结构 | 前奏/主歌/副歌/桥段，重复段合并 | 学习成本（重复度越高越易学） | ❌ 需 `Score` v2/段落标记 |
| 和弦 | 和弦进行、转位、七和弦、织体 | `chord.*`、`texture.*` | ⚠️ 三和弦/连接可；转位/七和弦待扩 |
| 旋律 | 音程、跳进、手位、指法 | `pos.*`、指法引擎输出 | ✅ |
| 节奏 | 附点、切分、十六分、拍号 | `rhythm.*` | ✅/⚠️ 切分启发式 |
| 调号 | 升降号数量 | `key.*` | ✅ |
| 织体 | 分解/柱式/半分解 | `texture.*` | ⚠️ 仅分解和弦启发式 |

### 4.3 输出：技能需求清单 + 难度向量

拆解引擎对每个维度产出一组技能 id，汇总为：

```
Decomposition {
  skills: string[]          // 所需技能 id 集合（去重）
  difficulty: Difficulty    // 主档 + 向量 + 修正，见 §5
  chunks: Chunk[]           // 结构块（P1 可由人工标注，P2 自动）
  warnings: string[]        // 启发式不确定项，供内容 QA
}
```

当前代码已能产出 `skills` + `difficulty`（`requiredSkillsForScore` + `rateScore`）；`chunks` 和 `warnings` 是 P1 的作者工具输出。

### 4.4 内容 QA（新增）

`src/repertoire/contentValidation.ts` 的 `validateSongContent(score, manifest)` 是作者工具/CI 的共用入口：

- 乐谱是否落在 MVP 词汇表内（`minLevelForScore >= 7` 直接错误）。
- manifest 声明难度是否**低于**引擎评级（低评会让用户挫败 → 错误）。
- 声明难度是否**高于**引擎评级（保守 → 警告）。
- `skillDeps` 与引擎识别结果是否一致（不一致 → 警告，人工确认）。
- 每个音的指法是否 1..5（`finger=0` 会让 demo 的 `Pianist` 访问 `fingers[-1]` 崩溃）。
- manifest bpm 与谱面 bpm 是否一致。

**已落地**：`npm run validate:content` 会扫描 `content/**/manifest.json`，输出每个包的错误/警告；也可以传入单个包目录。作者不需要写测试就能校验。

### 4.5 输入格式（新增）

| 格式 | 支持 | 说明 |
|---|---|---|
| `score.json`（内部 `Score`） | ✅ P0 | 手工/工具生成；必须带指法 |
| MusicXML | ✅ P0.5 | 单声部/简单和弦子集（`npm run import:musicxml`）；越界项报错不降级 |
| MIDI | ❌ P3 | 时值/声部/踏板脏，需量化+人工修 |
| 音频 → 自动扒谱 | ❌ 非目标 | 不做 |

## 5. 难度评级

### 5.1 主档公式（已落地）

难度不是一个数，而是一个**向量 + 一个主档**。主档计算：

```
词汇表最小容纳档 = minLevelForScore(score)        // 1..6，超纲 = 7
所需技能最高档   = maxSkillLevel(requiredSkills)  // 0..6
baseLevel       = 词汇表最小容纳档 === 7 ? 7 : max(词汇表最小容纳档, 所需技能最高档)
最终档           = baseLevel === 7 ? 7（超纲，不上架）
                 : clamp(baseLevel + 速度修正 + 重复修正 + 长度修正, 1, 6)
```

为什么取 `max` 而不是只看技能：

- 只看技能最高档会漏掉"词汇表不允许"的谱（例如超出手位/和弦限制）。
- 只看词汇表最小档会把"L4 分解和弦编配"评成 L1–L2（v0.1 的问题）。
- 取 `max` 后，**任意一边超纲都会把难度抬上去**。

**保守算法**：最终档向下取整（宁评低不评高），半档体现在 `label` 的 `+` 上；向下修正合计最多 `-0.5`，避免把 L2 曲子直接标成 L1。

### 5.2 难度向量（已落地）

`Difficulty.vector` 只用于解释"难在哪"，不参与最终档计算：

| 维度 | 来源 | 用途 |
|---|---|---|
| `rhythm` | `rhythm.*` 最高档 | UI 显示"节奏难" |
| `coordination` | `hands.*` 最高档 | 显示"双手协调难" |
| `key` | `key.*` 最高档 | 显示"调号难" |
| `handPosition` | `pos.*` 最高档 | 显示"手位/跳进难" |
| `harmony` | `chord.*` 最高档 | 显示"和弦难" |
| `texture` | `texture.*` 最高档 | 显示"织体难" |

长度通过 `adjustments.length` 单独表达（>24 小节 +0.5，>48 小节 +1），不塞进向量。

### 5.3 评级表（沿用 MVP 词汇档）

| 档 | 典型曲目形态 |
|---|---|
| L1–L2 | 单旋律 + 根音/简单伴奏，五指范围，无黑键或一个升降 |
| L3 | 旋律 + 原位三和弦伴奏，简单临时升降 |
| L4 | 旋律 + 分解和弦，两个升降以内，手位扩张 |
| L5–L6 | 完整织体，附点/切分/十六分，含跳进 |

> **注意**：v0.1 写的"L4 含连线"当时无法表达。**连线已补齐**（`NoteEvent.tie`，见 §1.2、§2.5）；**弱起小节也已补齐**（`Score.pickup`，见 §1.1、§6.3）；只剩反复记号还是 `Score` 后续版本的工作。

### 5.4 声明值与计算值（新增）

manifest 的 `difficulty` 是**作者声明**，引擎评级是**计算值**。两者关系：

| 情况 | 处理 |
|---|---|
| 声明档 = 计算档 | 通过 |
| 声明档 > 计算档 | 警告（保守，可接受；但可能让用户错过更简单的曲目） |
| 声明档 < 计算档 | **错误**（低评会让用户挫败，也破坏解锁规则） |
| 计算档 = 7（超纲） | 错误（词汇表不支持） |

`difficulty.level` 允许 1..7，其中 7 只用于"超纲"标记；曲库不应上架 7。

### 5.5 当前修正项

| 因子 | 作用 | 规则 |
|---|---|---|
| 速度（BPM） | ± | 相对档位锚点：+24 BPM → +1，+12 → +0.5；-24 → -1，-12 → -0.5 |
| 重复度 | − | `repeat >= 0.8` → -1；`>= 0.5` → -0.5；合计向下最多 -0.5 |
| 长度 | + | >24 小节 +0.5；>48 小节 +1 |

锚点 BPM：L1–L3 60，L4–L5 52，L6 48。锚点来自 MVP 过关测试速度，后续可用真实用户数据校准。

## 6. 编配分级

### 6.1 一首歌，多个难度版本

同一首歌编配成多个难度版本，是"任何水平都能弹喜欢的歌"的开关，也是持续成就线。

| 编配档 | 右手 | 左手 | 对应技能 | P1 是否可做 |
|---|---|---|---|---|
| L2 版 | 单旋律（八分） | 根音全音符/二分 | `pos.five`、`rhythm.eighth` | ✅ |
| L3 版 | 旋律 | 原位三和弦（四分） | `chord.triad`、`chord.progression` | ✅ |
| L4 版 | 旋律（可加简单装饰） | 分解和弦 | `texture.broken` | ✅（不含连线） |
| L4+ 版 | 旋律 + 连线 | 半分解/柱式 | `texture.comp` | ⚠️ 词汇就位（`tie`），只差真实曲目的编配 |
| L5 版 | 旋律（附点、手位扩张）+ 跨小节延音 | 柱式原位三和弦 | `rhythm.dotted`、`pos.shift` | ✅ 原创示范曲《晨歌》（弱起小节 + 连线 + 三个手位） |
| L5/6 版 | 完整旋律 | 附点·切分·十六分织体 | `rhythm.dotted/syncopation/sixteenth` | ❌ 等词汇扩展 |

"先弹 L2 简化版 → 升级后弹 L4 完整版" = 一条持续的升级路径，同一首歌反复带来新鲜感。

### 6.2 编配质量的自动校验

编配完成后，按三层校验：

1. **引擎校验**（已落地）：`validateSongContent` 检查词汇表、难度、技能声明、指法。
2. **物理校验**（P1）：示范演奏层跑一遍，检查是否撞键、是否够得着、指法是否顺。
3. **人工试弹**（P1）：内容作者/测试用 MIDI 键盘试弹，确认音乐性（引擎不能判断"好不好听"）。

### 6.3 编配边界（新增）

- **不把"完整原曲"作为 P1 目标**：先做 8–16 小节教学版；完整版需要反复/段落/速度地图。
- **不把"自动编配"作为 P1 目标**：P1 的编配是人工/半自动；自动编配（MIDI → 多版本）留到 P3。
- **不承诺"原调原速"**：教学版可以移调/降速，但必须在包名/详情页标注。

### 6.4 歌曲、编配与目录（新增）

v0.1 的 `id = song.xiaoxingyun.l3` 把难度写进 id，重新评级时 id 会变，导致用户进度/收藏丢失。改为三层：

```
Song (歌曲)
  id: song.xiaoxingyun
  title: 小幸运
  composer: ...
  arrangements: [
    Arrangement { id: arr.xiaoxingyun.simple, songId: song.xiaoxingyun, packageId: pkg.xiaoxingyun.simple, level: 2 }
    Arrangement { id: arr.xiaoxingyun.standard, ... , level: 3 }
    Arrangement { id: arr.xiaoxingyun.full, ... , level: 4 }
  ]
```

- `package.id` 是包的唯一 id，**不含难度**；难度放 `difficulty.level`。后缀用 `simple`/`standard`/`full` 这类语义，而不是 `l2`/`l3`——重新评级时 id 不变。
- `songId` / `arrangementId` 是 manifest 字段；`songTitle` / `composer` 供曲库展示。曲库目录（catalog）是 P0.5 的独立索引，由 `buildCatalog` 从 manifest + 引擎评级聚合生成。
- 同一首歌的多个编配共享 `songId`，用户"升级编配"时进度可继承（按技能/段落，不按包 id）。

## 7. 两条学习路径

### 7.1 路径 A · 按部就班

- 沿技能图谱拓扑序推进，复用 MVP 识谱/视奏课程作为技能载体。
- **每一级挂曲目里程碑**：该档过关后，解锁 2~3 首恰好该档能弹的曲目（数据包），立即获得"我能弹真曲"的正反馈。
- 目标：基础扎实、曲库随等级自然扩大。
- **前置**：L3 预备课已提供 L2 之后的入口（§2.6）；但完整 L3 过关测试与 L4–L6 课程仍需补，否则路径 A 只能停在 L3 预备阶段。

### 7.2 路径 B · 先选曲

1. 用户在曲目包选一首想弹的歌（曲库按难度评级展示）。
2. 拆解引擎 → 技能需求清单 → 与用户掌握状态比对 → 得到"缺的节点"子图。
3. 生成**最小补短板清单**，用 MVP 识谱课的 5 分钟轻负荷练习逐个补齐（沿用"一课一个新点"哲学，避免纯硬啃曲子）。
4. 补齐后进入曲目跟弹（MIDI 识别评测 + 示范演奏对照）。

**补短板算法**（已落地）：

```
required = requiredSkillsForScore(score)
mastered = masteredSkillIds(ledger, hand)     // 按目标曲目的手别
missing  = missingSkills(required, mastered)  // 含前置闭包
```

- `missingSkills` 会把未掌握的前置一起补进来，保证学习顺序。
- 路径 B 的"补短板"不是"必须先把整级学完"，而是"只学这首歌缺的节点"。
- **护栏**：补短板课只写 `learning`，不写 `passed`；只有该技能的过关测试才能写 `passed`。这样路径 B 不能靠"弹完一首歌"绕过识谱解锁。

### 7.3 进度账本（新增，已落地）

**问题**：v0.1 说"一个技能节点只有一个 state"，但 MVP 的 L1 是左右手分别过关的；同一技能在不同速度下掌握程度也不同。一个 `state` 表达不了。

**方案**：`src/repertoire/skillState.ts`

```
key = skillId + "@" + hand        // hand: RH | LH | both | none
value = {
  state: locked | learning | passed,
  bpm?: number,
  confidence: 0..1,
  masteredAt?: number,
  lastPracticedAt?: number
}
```

关键规则：

| 规则 | 说明 |
|---|---|
| 课内完成 → `learning` | `applyLessonCompletion` 只写 learning，confidence +0.15 |
| 过关测试 → `passed` | `applyLevelTestPass` 才写 passed，confidence=1 |
| 曲库跟弹 → `learning` | `recordFollowPractice` 记一次练习和当时的 bpm，同样不写 passed（§7.7） |
| 单手技能 | `clef.treble` 只写 RH；`clef.bass` 只写 LH；右手 L1 测试不会把低音谱标成通过 |
| 双手技能 | `pos.*` / `chord.*` / `hands.*` 默认要求 RH+LH 都 passed；也可用 `both` 记录"双手一起学会" |
| 与手无关 | `rhythm.*` / `key.*` 存 `none`，左右手共用 |
| 旧数据迁移 | `migrateProfile(profile)`：以档案里的账本为底，再把 `l1RightPassed`/`l1LeftPassed` 分左右手、`l2Passed` 写双手叠上去 |
| 遗忘 | `staleSkills(ledger, now, 30)` 返回超过 30 天未练的已掌握技能，用于复习提示 |
| 单一账本 | 路径 A/B 写同一份账本；不存在"课程进度"和"曲目进度"两套 |

**存储**：账本序列化后存在 `Profile.skillLedger`，随用户档案持久化；`mergeProfile` 加载时只做结构校验——认不出的 `state` 降级成 `learning`，绝不让坏数据把技能变成已过关。图谱里已删除的技能 id 无需清理：读取方都遍历图谱再查账本，对不上的条目永远不会被匹配到。

### 7.4 解锁/评测门槛（新增）

| 事件 | 写入账本 | 是否解锁下一级/视奏 |
|---|---|---|
| 完成一节微课 | `learning` | ❌ |
| 该级过关测试 | `passed` | ✅（按 MVP 规则） |
| 弹完一首曲目（跟弹） | 对应技能的 `confidence` / `bpm` 更新，但不写 passed | ❌（可显示"曲目完成"，但不替代识谱过关） |
| 路径 B 补短板课 | `learning` | ❌ |
| 补短板课后的技能测试 | `passed` | ✅ |

这个门槛是产品价值观：**"能跟弹一首歌"不等于"识谱过关"**。曲目完成给成就，识谱过关才给解锁。

### 7.5 评测：单音 vs 整曲（新增）

MVP 的 MIDI 识别是单音/逐音对齐。曲目模式需要：

- **分段评测**：按 2–4 小节一段，段内允许重来；整曲分数 = 各段加权。
- **双手分离**：先右手、再左手、再合手；每只手单独评分。
- **时间容忍**：不是"错一个音就断"，而是按拍点窗口（如 ±80ms）和音高匹配率评分。
- **速度/稳定度**：实际 BPM、节奏偏差、停顿次数。
- **示范对照**：用户演奏 vs 示范的偏差可视化（音高/时值/指法）。

P1 先做"分段 + 单手 + 音高/拍点匹配"，整曲连续评测放 P2。

### 7.6 跟弹的落地方式（已实现）

**位置在曲库页就地展开，不跳视奏页**（`src/ui/ScoreFollow.vue`）。

早期实现是"切出这一段的谱子 → 交给视奏页"，两个问题：

1. 视奏页的口径是"弹错也不要停，弹完再来复盘"，跟"把这两小节练熟"不是一回事；它还带 25 秒看谱倒计时，对着已知片段纯属干扰。
2. 回来时段落选择丢失，一段一段往下练要反复重选。

现在的闭环：选编配 → 选段 → 就地展开跟弹 → 一小节预备 → 按网格弹 → 看结论 → 再跟一遍。

**判定模型**（`src/practice/rhythm.ts` 的 `planForScore` + `gradeRhythm`）：

| 概念 | 规则 |
|---|---|
| 槽位（slot） | 一拍一个；同一拍上的左右手、和弦合并成一个槽位，必须一起按 |
| 推进 | 槽位里**所有目标音都按下**才往前走；弹错/多弹不推进 |
| 放行 | 时钟走到下一个槽位起点还没弹，就认漏并继续——否则漏一个音整段错位 |
| 多弹 | 不属于这一段的音只提示、不计分（`多弹了 N 个音`），避免一两次手滑毁掉整段结论 |
| 时间 | 一律用**拍**，容差 `ON_BEAT_TOLERANCE = 0.25` 拍；换速度时口径不变 |
| 音长 | `note-off` 到达后按每个音的目标时值判「按足了没有」（`MIN_HELD_RATIO = 0.6`），只作附加观察，不影响对错 |
| 结论 | `音高与节拍都对了 N / M 音（x%）`＋系统性偏早/偏晚＋偏得最多的三拍＋弹短的音数 |

**看到的和判的是同一份谱子**：跟弹打开时，谱面、示范播放器、播放条都切到这一段（`staffScore`）。否则谱面画整首、网格判两小节，用户不知道在练哪一段。

**为什么复用 `RhythmGrid`**：乐理练习的旋律跟弹已经在用同一块网格（音名压拍线、落点绿/红、漏音空圈）。曲库这边多出来的只有"多音槽位"——音名取最高音，后面跟 `+N` 表示这一拍还要多按几个键。

**边界**：

- 不判指法、力度；指法只作为谱面上的示意。
- 曲目完成不等于识谱过关（§7.4）：整段弹对只写**练习证据**，不写 `passed`，详见 §7.7。

**音长只观察、不判错**：`note-off` 到了就按每个音自己的目标时值比一次，短于六成在结论里说一声「N 个音按得太短，长音符要按住不放」，但不折算进百分比。原因是连音、保持音在不同教材里口径不一，拿它判对错会误伤正确的演奏；而初学者最普遍的毛病——全音符弹成四分音符——用「观察」就足以点出来。同一拍上左右手时值经常不同（低音铺满全小节、右手走四分音符），所以每个音记自己的目标时值（`RhythmSlot.targetBeats`），不拿最长的那一个要求所有音。

**同一把尺子也量视奏复盘**：阈值与判定放在 `src/domain/hold.ts`（`MIN_HELD_RATIO` + `isHeldEnough`），跟弹与视奏页共用，两条路径的口径不会各自漂移。视奏的判题在 `domain/compare.ts`（`CompareResult.shortNoteIds`），`SightView` 现在也记录 `note-off`，复盘页在统计行下方多一行「N 个音按得太短，长音符要按住不放。」——同样只观察：不影响 `isPass`、不进错题本、谱面上不多一种颜色。和弦路径按事件逐个音判（同一拍上左右手时值不同，见上），按错的音不参与。

### 7.7 跟弹成果写进账本（已实现）

早期的"已弹对"只是页面里的一个 `Set`，刷新就没；技能账本（§7.3）也只有关卡测试一条写入路径。于是"先选曲"路径练得再多，缺技能清单上看不出任何变化——技能图谱成了静态展示。

现在整段弹对（`onCount === total`）会做两件事：

| 写入 | 内容 | 语义 |
|---|---|---|
| `Profile.followedSegments` | 切片谱 id（`score.ode-to-joy.l2.m1-2.RH`） | 分段下拉里的 `· 已弹对`，刷新不丢 |
| `Profile.skillLedger` | 这一段涉及的技能各记一次练习：`state: learning` + `bpm` | 技能清单里显示 `练过 · 92 BPM` |

**只写 `learning`，不写 `passed`**：把一首曲子弹下来不等于会认谱——学生可以盯着指法数字或靠肌肉记忆弹完一段。识谱是否过关仍由各级过关测试判定（§7.4），跟弹证据只回答"在什么速度下练过"。

**三个实现要点**：

1. **账本从档案出发**：`migrateProfile(profile)` 不再从空账本重建，而是以 `profile.skillLedger` 为底，再把过关状态叠上去。`recordPractice` 的既有语义保证 `passed` 不会被普通练习降级，所以两条路径可以安全共用一份状态。
2. **按手别记**：切片谱 id 自带手别后缀，换手就是另一份谱子——右手弹顺了不代表左手也会，同一段要重新弹对。
3. **坏数据降级而不是信任**：`mergeProfile` 对账本只做结构校验，认不出的 `state` 一律降成 `learning`。坏数据最多丢掉一次过关，绝不可能把没过的技能变成已过关。

**证据参与补短板排序**：缺口集合仍由 `missingSkills`（缺什么 + 未掌握的前置）决定，`missingSkillOrder` 只改展示顺序——档位升序保证前置先学，同档里「练过」的排前。练过的技能是半熟：学生在曲子里已经能把它弹下来，只差认谱过关，先把这些补成 `passed` 最快，也让学生看见「先选曲」的练习确实在推进按部就班的关卡。缺口的就绪文案随之多说一句：「还差 8 项技能，其中 3 项已经练过。」

**耗时估算回答「还差多久」**：`estimatePracticeMinutes(missing, ledger)` 把缺口折算成分钟——按档位给基准（L1 5 / L2 8 / L3 12，越往后一课容量越大），练过的打三折（曲子已经能弹下来，只差认谱过关，复习比从头学快）。**没有微课的技能不计入**：没有课就谈不上「多久补完」，界面已经用「暂无微课」说过一次，估算只覆盖「有微课的部分」，宁可少算也不虚报。分钟数是粗估，文案用「约」字开口，不作为承诺。

## 8. 示范演奏层（piano-buddy-demo 的定位）

### 8.1 现状

`piano-buddy-demo` 是 Three.js 钢琴 3D 演奏动画（约 **1723** 行 TS，不是 v0.1 写的 2037），核心管线已闭环：`NoteEvent` 事件流 → MIDI→88 键 3D 坐标 → 掌位/手腕弹簧规划 + 掌位闭合解 + FK 自标定 → 双手骨骼动画。触键精度毫米级（press 0~1mm、闲置离键面 0±2mm）。

### 8.2 定位

**它是"曲目学习"板块的示范演奏层（Playback/Presenter），不是独立产品。** 两条路径共用——路径 A 的曲目里程碑、路径 B 的"看示范再弹"，都靠它提供 3D 双手标准演示。

### 8.3 融合管线与 Motion IR（已落地）

```
[piano-buddy Score + 指法]
        │  scoreToMotion()
        ▼
MotionScore { notes: MotionNote[], bpm, totalBeats }
        │  toDemoEvents()
        ▼
DemoNoteEvent { midi, start, end, hand, finger, vel }  →  [Pianist IK] → [3D]
```

- **Motion IR**：`src/repertoire/motion.ts`。`MotionNote` 用拍（onsetBeats/durationBeats）描述，保留和弦内每个音和指法；`toDemoEvents` 用 bpm 转绝对秒，demo 不需要理解主项目的 `Score`。
- **硬校验**：`validateMotion` 拒绝 `finger` 不在 1..5、midi 越界、负拍点、非正时值、同手同音非法重叠。**`finger=0` 是当前 demo 的真实崩溃点**（`Pianist.loadScore` 会访问 `fingers[-1]`），所以曲目包内容 QA 必须先过这一关。
- **可信指法**：把 demo `scores.ts` 手写指法替换为 pianoplayer 指法引擎输出（或直接用 Motion IR 的 finger）。
- **时间桥接**：主项目用拍、demo 用秒；`toDemoEvents` 已做 `60 / bpm` 转换。
- **导出与 demo 接入**：`npm run export:demo` 把 L2《欢乐颂》写成 `piano-buddy-demo/src/data/ode-to-joy.l2.motion.json`（默认取同级目录，可用 `DEMO_DIR` 覆盖）；demo 的 `motionAdapter.ts` 再做一次 finger/midi/时值校验并转成自己的 `Score`。demo 已把《欢乐颂》设为默认曲目，复用现有 HUD 的播放/暂停/seek/0.5–1.5x 变速。

### 8.4 教学播放控制（新增）

v0.1 只说了"看示范"，但教学场景需要的不只是播放：

| 控制 | 用途 | 现状/做法 |
|---|---|---|
| 播放/暂停/重播 | 基础 | 主项目 `createPreviewPlayer` 已提供 play/pause/stop；demo clock 已有 |
| 速度 50%–100% | 慢练 | `PreviewPlayer.setSpeed(0.25–2)`；demo 的 clock 支持倍率 |
| A–B 循环 | 分段练 | demo 侧 P1 已实现（`Clock.loopRange` + HUD A/B/清除，回绕保留溢出）；主项目曲库页已接「循环本段」——循环区取自当前分段（小节坐标经 `segmentBeatRange` 转拍坐标），到末端回绕重播、不触发 `onEnd`，跟弹时循环整个播放区 |
| 单手独奏/静音 | 分手练 | `PreviewPlayer.setHand("RH"/"LH"/"BOTH")`；曲库页已接双手/右手/左手切换；demo 侧 P1 已用双手 GainNode 实现静音，且单手切换已接 3D 手部（`Pianist.setHandMode`：停用的手收回待机高度，琴键不下沉；单一事实源在 pianist，HUD 只发命令） |
| 预备拍/节拍器 | 跟弹 | 主项目节拍器 + demo 同步 |
| 拖动进度 | 回看 | `PreviewPlayer.seek(beat)` 会停止当前节点并从新拍点重排；曲库页已接滑杆，demo 手部状态重置待做 |
| 谱面跟随 | 看谱 | demo 侧 P1 已实现音符轨道（钢琴卷轴 + 音名，非 VexFlow），与 3D 共用一个 clock；五线谱跟随仍待主项目对接 |

**工程提醒**：`src/audio/preview.ts` 现在保留 `previewScore` 作为一次性播放兼容入口，并新增 `createPreviewPlayer`。Web Audio 已调度的 oscillator 不能真正暂停，所以 pause/seek/变速采用"停止当前节点 → 从新拍点重新调度"；长曲按 0.2 秒窗口调度，不会一次创建几千个节点。曲库页已接入播放/暂停/重播、0.5x/0.75x/1x、单手切换、seek 和「循环本段」（`setLoop`，循环区含头不含尾，到末端回绕重播而不触发 `onEnd`）；demo 示范层 P1 已补齐 A–B 循环、音符轨道与静音，与主项目现在是同一套能力。

### 8.6 反向复用与边界

示范演奏层反过来当**指法引擎和难度评级的可视化调试器/物理校验器**：跑一套指法，肉眼看是否撞键、是否够得着；跑一首编配，验证其难度评级是否成立。

但**它不是物理真理**：demo 的手部模型是近似，碰撞/够得着只能当"可疑信号"，最终要人工试弹。P1 的验收是"能发现明显不合理的指法"，不是"自动证明编配可弹"。

## 9. 数据包 Schema 设计

### 9.1 包结构

```
<package>/                     # 一个数据包 = 一个目录（或 zip）
├── manifest.json              # 元数据 + 依赖声明 + 校验
├── content/                   # 内容文件（乐谱/编配/音频/模型引用）
│   ├── score.json             # 曲目：编配（含指法）
│   └── ...
└── ...
```

### 9.2 manifest.json（P0 已实现字段）

```jsonc
{
  "schemaVersion": 1,          // 包结构版本，向后兼容演进
  "id": "pkg.xiaoxingyun.standard",  // 包稳定唯一 id；不要把难度写进 id
  "name": "小幸运 · L3 编配",
  "type": "song",              // course | song | practice
  "version": "1.0.0",          // semver
  "songId": "song.xiaoxingyun",
  "arrangementId": "arr.xiaoxingyun.standard",
  "songTitle": "小幸运",       // 曲库歌曲名；同一 songId 下必须一致
  "composer": "Example Composer",
  "minAppVersion": "2.0.0",    // 旧 App 读到新包时提示升级

  "skillDeps": ["chord.triad", "key.one-flat"],   // 技能依赖（引用 §3 图谱）
  "difficulty": {
    "level": 3,
    "bpm": 96,
    "repeat": 0.8,             // 0..1
    "len": 24                  // 小节数，不是秒
  },
  "assets": ["content/score.json"],
  "checksum": "sha256:9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08", // 声明后按 assets 顺序真算并比对
  "license": "CC-BY-NC",       // 兼容旧字段
  "rights": {                  // 新增：作曲/编曲/录音可分别授权
    "type": "licensed",        // public-domain | licensed | original | user-imported
    "attribution": "...",
    "territory": "CN",
    "expiresAt": "2027-12-31"
  }
}
```

### 9.3 关键规则（P0 已实现）

| 规则 | 状态 | 说明 |
|---|---|---|
| **依赖声明** | ✅ | `skillDeps` 引用图谱 id；未知 id 报错；重复去重 |
| **版本化** | ✅ | `schemaVersion` 只接受 1；`version`/`minAppVersion` 必须 semver |
| **ID 格式/稳定约定** | ✅/⚠️ | 代码只校验字符集（小写字母、数字、点、下划线、短横线）；“发布后不改 id”靠作者/CI 约定，catalog 迁移另做 |
| **路径安全** | ✅ | `assets` 必须是包内相对 POSIX 路径；拒绝绝对路径、盘符、反斜杠、`.`/`..`、NUL；最多 64 个 |
| **字段校验** | ✅ | 难度 1..7、BPM 20..300、repeat 0..1、len ≥0；`assets` 非空 |
| **版权/到期** | ✅ | `license` 保留；`rights` 支持 public-domain/licensed/original/user-imported；`expiresAt` 校验为合法日期，过期给 warnings；`buildCatalog` 跳过到期编配（下架）并记警告，不阻断构建 |
| **校验和** | ✅ | 声明 `checksum` 时按「`assets` 声明顺序拼接 `路径\\n内容`、资源间以 `\\n` 分隔」重算 sha256/sha512 并比对；环境没有 Web Crypto 时降级为警告。改内容/改路径/改顺序都会让摘要变化 |
| **大小上限** | ✅ | 单文件 512 KB、合计 4 MB（`MAX_ASSET_BYTES` / `MAX_TOTAL_BYTES`，UTF-8 字节），超限拒绝加载 |
| **签名** | ❌ | P3；先本地包 |
| **未知字段** | ✅ | 顶层 / `difficulty` / `rights` 的未知字段收进 `warnings`（不报错），帮作者发现拼写错误；`validate:content` 与 `build:catalog` 会打印 |

### 9.4 三类数据包

| 类型 | 内容 | 示例 |
|---|---|---|
| 课程包（course） | 技能课程序列 | 按部就班的识谱/视奏课程，映射技能图谱 |
| 曲目包（song） | 歌曲 + 多编配版本 | 一首歌带 L2/L3/L4 三个编配 |

### 9.5 曲库目录（P0.5，已落地）

曲库列表不靠扫描磁盘/目录顺序，而由 `src/repertoire/catalog.ts` 的 `buildCatalog` 聚合生成 `content/catalog.json`：

```
Catalog {
  version: 1,
  songs: [
    { songId, title, composer?, arrangements: [
      { arrangementId, packageId, name, level, label, bpm, measures, skillDeps, rights? }
    ]}
  ]
}
```

- `level` 用**引擎评级**，不是作者声明；`label` 保留 `L2+` 这样的体感半档。
- `npm run build:catalog` 先跑 manifest/内容 QA，任何 error 都不写文件；`npm run build:catalog -- <content目录> <输出路径>` 可指定输入输出。
- `buildCatalog` 拒绝：缺 `songId`/`arrangementId`/`songTitle`、重复 `packageId`/`arrangementId`、同一 `songId` 下标题或作曲者不一致、超纲（level 7）。
- 同一歌曲的编配按 level 排序；歌曲按标题排序。`rights` 原样带出，供后续下架/地区过滤。
- `test/catalog.test.ts` 会把 `content/catalog.json` 与当前包聚合结果逐字段比对，防止忘跑构建脚本。
- 当前产物：1 首歌曲（《欢乐颂》），3 个编配（L2/L3/L4）。

## 13. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| **曲库承诺过大** | 用户预期"什么歌都能弹"，实际只有受控曲库 → 失望 | 文案/PRD 明确"简化版/教学版"；P1 只上当前词汇表能表达的曲；§1.2 边界写进验收 |
| **L4–L6 课程断档** | 路径 A 在 L3 预备课后无完整课程可上 | L3 完整课程（L3R-1..4 + 过关）与 9 节预备课已落地；L4 有两节乐理预备课过渡；L4–L6 完整课程在 P2 排期；文案明确"L3 只是预备入口" |
| 版权 | 法律风险 | 数据包版权隔离；平台只发无版权包；授权曲目独立渠道或用户导入；`rights.expiresAt` 到期下架 |
| schema 设计不周 | 后期迁移成本高 | P0 先定稿图谱 + schema；`schemaVersion` 分支；新增字段可选 |
| 编配质量差 | 核心体验受损 | 引擎 QA + demo 物理校验 + 人工试弹三层 |
| 只弹曲不练基础 | 基础不牢 | 路径 B 5 分钟补短板；`passed` 只能由测试写；曲目完成不解锁视奏 |
| 难度评级不准 | 挫败/流失 | 保守算法；声明低于引擎评级直接 error；P1 用人工试弹校准 |
| 拆解启发式误判 | 补短板清单不准 | 曲目包必须带指法；`validateSongContent` 警告；人工确认 `skillDeps` |
| 数据包安全 | 恶意/损坏数据 | 未信任输入：路径白名单、数量/大小上限、字段校验、禁执行；签名 P3 |
| demo 代码漂移 | 适配层失效 | Motion IR 是唯一协议；demo 只依赖 `DemoNoteEvent`；P1 加适配层契约测试 |
| 播放控制返工 | "看示范"体验差 | P1 先把 `preview.ts` 改成时钟/调度器，再做 UI |
| 过度设计 | 交付变慢 | P0.5 只做 1 首歌 × 3 编配；市场/自动编配/签名留 P3 |

## 附录 B · 推荐的第一首切片曲目

选择标准：

1. 公版或原创，无版权风险。
2. 当前词汇表可表达：C/F/G 大调、4/4、单声部旋律、三和弦/根音伴奏。
3. 旋律熟悉、8–16 小节可循环。
4. 能做出 L2/L3/L4 三个明显不同的编配。

候选（按优先级）：

- **《欢乐颂》**（公版）：C 大调、4/4，旋律 E4–G4 全在 C 五指位；L2 根音、L3 三和弦、L4 分解和弦都能做。**已落地为 `content/song.ode-to-joy.l2/l3/l4` 三档编配**，风险最低。
- **《小星星》**（公版）：C 大调、4/4，但标准旋律含 A4；A4 在 C 五指位之外，L2/L3 的 `expandEnds=false` 不允许，需要 L4 扩张或移调/改音。**不适合作为第一首 L2**。
- **原创 8 小节练习曲**：完全可控，但用户认知度低，适合作为 L3/L4 的技术配套。

> 第一首不要选有切分/小调/A4 的流行歌——不是它们不重要，而是当前 `Score` 表达不了或会跨手位，会把"内容问题"误判成"引擎问题"。（弱起已经不是障碍：`Score.pickup` 能表达，导入器也会自动识别。）

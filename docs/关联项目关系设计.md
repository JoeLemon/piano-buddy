# 关联项目关系设计

> **版本**：v1.0（重设计）
> **日期**：2026-10-23
> **前置文档**：`关联项目梳理.md`（两项目事实盘点）、`docs/二期-曲目学习路径.md` §2.4 / §8（示范层定位与集成边界）
> **本文要解决的问题**：原梳理把三个项目写成「并列清单 + 三条箭头」，只回答了「有什么」，没回答「它们**以什么方式**关联、谁说了算、改一处会波及哪里」。本文重设计关系模型。

---

## 0. 重设计摘要

**旧模型的问题**：把 piano-buddy 画成「中心节点」，另外两个画成「挂在旁边的项目」。这会误导出两种错误动作——把 SightReading 当依赖去接、把 demo 当子模块去并。

**新模型的一句话**：

> 三个项目不是同一种关系。piano-buddy 是**能力内核**；demo 是受**版本化契约**约束的**外向表现端**；SightReading 是**旁系参照产品**，只提供语义与方法，不提供运行时依赖。

三条关系分属三种类型，必须分开治理：

| 关系 | 类型 | 方向 | 耦合载体 | 共享代码 | 一句话判据 |
|------|------|------|---------|---------|-----------|
| piano-buddy → demo | **供给关系** | 单向（上游→下游） | Motion IR（版本化 JSON） | 否 | 换掉 demo 的渲染器，主项目不用改一行 |
| SightReading → piano-buddy | **参照关系** | 单向（语义影响） | 设计文档 + 交互语义 | 否 | 删掉 SightReading，主项目仍能构建运行 |
| demo ↔ SightReading | **无关系** | 无 | 仅同属钢琴学习域 | 否 | 两者从不知道对方存在 |

判据是整个模型的试金石：**任何「删掉对方会不会坏」的测试，都应当得到上表的答案。** 目前三条都成立。

## 1. 关系类型学：先分类，再谈关联

### 1.1 三个项目各自是什么

| 项目 | 本质 | 拥有的「真理」 | 不拥有的 |
|------|------|--------------|---------|
| **piano-buddy** | 学习应用 + 领域内核 | 乐谱模型、指法求解、技能图谱、难度评级、内容包 schema、Motion IR 定义 | 3D 渲染、内容运营后台、账号体系 |
| **piano-buddy-demo** | 表现层运行时 | 手部骨骼装配、掌位/腕部演算、相机与 HUD、触键精度 | 指法决策、课程逻辑、难度判断、内容编辑 |
| **00-SightReading_3.0** | 独立纵向产品 | 出题引擎、教师 CMS、云同步、账号与统计 | 曲目学习、3D 示范、指法求解、内容包分发 |

### 1.2 为什么不能合并

- **piano-buddy 不能吸收 demo**：three.js 会进主包（当前主包 1.15 MB / gzip 372 KB，二期明确「不把 three 打进主包」）；且 demo 的骨骼/GLB 认知负担与学习应用无关。
- **piano-buddy 不能吸收 SightReading**：SightReading 是完整的双端产品（CMS + 学生端 + Supabase 18 个迁移 + 账号白名单），合并等于把「内容运营系统」塞进「学习应用」，职责与部署形态都不同。
- **demo 不能反向吸收主项目**：一旦 demo 读 `Score`，主项目的模型演进就会把 3D 动画拖下水，契约消失。

### 1.3 三层关系图

```
┌──────────────────────────── 参照关系（无运行时耦合） ────────────────────────────┐
│  00-SightReading_3.0                                                            │
│  交互语义 / 出题方法 / 音频方案 / 规格流程  ──(文档与经验)──▶  piano-buddy        │
└─────────────────────────────────────────────────────────────────────────────────┘

┌──────────────────────────── 供给关系（版本化契约） ──────────────────────────────┐
│  piano-buddy（能力内核）                                                        │
│  Score + 指法 ──scoreToMotion──▶ MotionScore ──toDemoEvents──▶ motion.json       │
│                                                        │                        │
│                                                        ▼  Motion IR（唯一接缝） │
│                                              piano-buddy-demo（表现层）          │
└─────────────────────────────────────────────────────────────────────────────────┘

         demo  ◀──── 无关系 ────▶  SightReading（仅同域，互不知晓）
```

## 2. 分层模型（能力栈）

按「谁在下游、谁在上游」重排，而不是按仓库并列：

| 层 | 内容 | 归属 | 变更频率 |
|----|------|------|---------|
| **L0 内容源** | 乐谱、编配、指法结果、数据包（manifest + score.json） | piano-buddy（作者工具/CLI） | 高（随曲目放量） |
| **L1 领域能力** | 指法引擎、技能图谱、难度评级、包校验、Motion IR | piano-buddy | 中（算法迭代） |
| **L2 学习应用** | 今日/课程/曲库/乐理、识谱视奏、复盘、MIDI 输入、谱面渲染、音频播放 | piano-buddy | 高（UI 迭代） |
| **L3 表现层** | 3D 双手动画、相机、HUD、播放控制 | demo | 低（已稳定） |
| **旁系** | 出题/CMS/云同步/统计/账号 | SightReading（独立产品） | 低（成熟维护） |

**关键推论**：L3 只依赖 L0/L1 的**输出物**，不依赖 L2 的任何实现。所以 demo 可以被替换成「视频示范」「2D 手型图」而不影响主项目架构——这是供给关系健康与否的检验标准。

## 3. 依赖图与三个契约面

### 3.1 依赖必须无环

```
piano-buddy ──C1──▶ demo
piano-buddy ◀··C2·· SightReading      （虚线 = 语义参照，非依赖）
demo        ×       SightReading      （无边）
```

三条红线：

1. **demo 不得 import 主项目源码**（含相对路径、软链、monorepo 隐式解析）。
2. **piano-buddy 不得 import demo 源码**，也不得把 three.js 列为依赖。
3. **SightReading 不得被任何一方 import**；参照只发生在「读文档、抄语义」层面。

### 3.2 契约面清单

| 契约 | 载体 | 版本策略 | 消费方 | 破坏性变更流程 |
|------|------|---------|--------|---------------|
| **C1 数据契约（Motion IR）** | `src/repertoire/motion.ts` 类型 + `motion.json` 文件 | `schemaVersion` 字段；v1 → v2 必须新增可选字段，不删不改语义 | demo `motionAdapter.ts` | 主项目改类型 → 同步 demo adapter → 双端 golden 用例通过 → 才可导出新曲 |
| **C2 语义契约（键盘/判题）** | `docs/键盘输入与音区导航.md` + `src/keyboard/layout.ts` | 文档为准，实现各自独立 | piano-buddy 自身 | 改语义先改文档，再改实现，再对照 SightReading 行为回归 |
| **C3 方法契约（架构参照）** | SightReading 的 `docs/` + `openspec/` | 无版本，采纳即复制语义 | 人（开发者） | 不强制同步；采纳时在新文档注明出处 |

### 3.3 C1 的字段级约束（现状）

`MotionNote` 现有 9 个字段，其中 7 个被消费、2 个是「预留但未消费」：

| 字段 | 消费情况 | 约束 |
|------|---------|------|
| `midi` | ✅ | 21..108（A0–C8） |
| `onsetBeats` / `durationBeats` | ✅ | ≥0 / >0；demo 侧 `spb = 60/bpm` 转秒 |
| `hand` | ✅ | `"L"` / `"R"` |
| `finger` | ✅ | **1..5 整数**；`finger=0` 是 demo 的真实崩溃点（`fingers[-1]`） |
| `velocity` | ✅ | 0..1；影响预备窗口与抬指高度 |
| `id` | ✅（调试/对账） | 唯一即可 |
| `voice` | ❌ 未消费 | P0 统一 0；多声部前不得赋非 0 值 |
| `tie` | ❌ 未消费 | 连音线语义未落地，导出时恒为 false |

**治理规则**：未消费字段是**契约负债**。要么在 v2 明确消费（`tie` 影响释放策略、`voice` 影响手部遮蔽），要么在 v2 删除。不允许「字段在、语义没人认」长期存在。

### 3.4 C2 的关键事实（避免混用坐标系）

- 屏幕琴键几何唯一来源：`src/keyboard/layout.ts`（88 键、7 音区、A0–C8、`zoneScrollTarget`/`cMarks`）。
- 乐谱渲染用的是**另一套局部键**：`src/notation/renderScore.ts` 的 `whiteKeyMidis()`（C3–C5）。
- **两套坐标不得互相换算**；SightReading 的 `FullPianoKeyboard` 只是「七区划分 + 缩略导航」的语义参照，其像素/几何参数不可直接搬。

## 4. 职责边界矩阵

`拥有` = 唯一事实源；`消费` = 读对方产出；`参照` = 只学语义；`不做` = 明确禁止。

| 能力 | piano-buddy | demo | SightReading |
|------|------------|------|--------------|
| 乐谱模型（Score） | **拥有** | 不做（只认 Motion IR） | 拥有自己的题库模型（互不相干） |
| 指法求解 | **拥有**（pianoplayer 移植） | 不做（只消费 `finger`） | 不做 |
| 技能图谱 / 难度评级 | **拥有** | 不做 | 拥有自己的 L1–L10（方法参照） |
| 内容包 / 内容 QA | **拥有**（schema + CLI） | 不做 | 拥有 CMS 运营流（形态不同） |
| 谱面渲染 | **拥有**（VexFlow 4） | 不做 | 拥有（VexFlow 5，独立封装） |
| 音频播放 | **拥有**（`src/audio/`） | P1 消费 | 拥有（Tone.Sampler，方法参照） |
| MIDI / 屏幕键盘输入 | **拥有** | 不做 | 拥有（语义参照，代码独立） |
| 3D 手部动画 | 不做 | **拥有** | 不做 |
| 课程 / 练习 UI | **拥有** | 不做 | **拥有**（独立产品） |
| 内容运营 / 账号 / 统计 | 不做（P3 前） | 不做 | **拥有** |
| 云分发 | 不做（P1 本地包） | 不做 | **拥有**（Supabase） |

### 4.1 五条不可越界的规则

1. **指法唯一事实源在主项目**。demo 手写指法只允许存在于「非导出曲目」（如《致爱丽丝》演示）；任何进入学习闭环的曲目，finger 必须来自指法引擎。
2. **demo 不做任何「决策」**：不选指法、不判难度、不决定教学顺序。它只做「给定事件 → 摆出手」。
3. **主项目不感知 3D**：Motion IR 里不出现手部尺寸、掌位、机位、骨骼名。
4. **参照不升级为依赖**：除非出现**第三个**消费方，否则不抽 `@piano-buddy/motion` 公共包（rule of three）。
5. **不做双向同步**：demo 的播放状态不回写主项目；主项目的进度不驱动 demo 内部状态（只通过 seek）。

## 5. 重叠与冲突分析（哪里在重复造轮子）

| 能力 | 重复出现在 | 现状 | 判定 | 处置 |
|------|-----------|------|------|------|
| 88 键 + 七音区键盘 | SightReading `FullPianoKeyboard` / piano-buddy `layout.ts` | 语义已对齐（2026-10-22），实现各自独立 | ✅ 合理重复 | 只同步语义，不抽代码；改语义时双端回归 |
| MIDI 接入 | SightReading `useMidi` / piano-buddy `midi/access.ts`+`ble.ts` | 平台策略一致（桌面 Web MIDI / Android BLE / iOS 待 Capacitor） | ✅ 合理重复 | 记录平台矩阵，不共享实现 |
| 音频 | SightReading `AudioEngine`(Tone) / piano-buddy `src/audio` / demo 自建 Web Audio | demo P1 已能按 MotionNote 发声（合成音色，不共享代码） | ✅ 合理分化 | demo 保持自包含；SightReading 的采样/静音解锁方案仍作参照，采样音色升级放 P2 |
| 谱面渲染 | VexFlow 5（SR）/ VexFlow 4（PB） | 版本不同、封装不同 | ✅ 合理重复 | 不合并；各自服务不同页面形态 |
| 和弦分析 | **SightReading 内部两套**：`core/engine/chordAnalyzer`（23 模板）与 `core/chords/chordCatalog`（7 目录） | 同一产品两个事实源 | ❌ 反面教材 | 主项目不复制此模式：和弦/音程目录必须单一事实源 |
| 指法 | piano-buddy 引擎 / demo 手写 | demo 仍是近似编排 | ⚠️ 待收敛 | P1 用导出指法替换 |
| 内容运营 | SightReading CMS+Supabase / piano-buddy 数据包 CLI | 规模不同：前者多教师多学生，后者作者本地 | ✅ 合理分化 | P3 若做在线曲库再评估 |

**结论**：重复本身不是问题，**同一产品内部出现两个事实源才是问题**。跨项目重复只要「语义对齐 + 代码独立」，成本可控。

## 6. 端到端数据流

### 6.1 正向：从内容到 3D

```
作者写谱/编配
   │  npm run validate:content（schema / 难度 / 指法一致性）
   ▼
数据包（manifest.json + content/score.json）
   │  导出时 annotateScore(fill-gaps) → Score + 指法（锚点保留、缺口求解）
   ▼
scoreToMotion(score)  →  MotionScore（拍单位，含每音 finger）
   │  toDemoEvents(motion, bpm)  →  DemoNoteEvent[]（绝对秒）
   ▼
npm run export:demo  →  ode-to-joy.l2.motion.json（落到 demo 仓库）
   │  demo: validateMotion() → motionToDemoScore()
   ▼
Pianist（相位机 + 掌位闭合解 + 方向 IK） → 3D 双手 + 琴键
```

### 6.2 反向：demo 作为「物理校验器」

demo 可以反过来验证指法/编配：跑一套指法，看是否撞键、是否够得着、手位是否跳得太远。

**但它不是物理真理**：手部模型是近似、无碰撞求解、琴键下沉由时间驱动而非指尖因果。因此产出只能是**可疑信号**，最终仍需人工试弹。P1 验收标准是「能发现明显不合理的指法」，不是「自动证明可弹」。

### 6.3 变更影响矩阵（改一处会波及哪里）

| 改动 | 直接影响 | 需要同步 | 风险 |
|------|---------|---------|------|
| `Score` 模型 | `scoreToMotion`、导出脚本 | demo adapter（若字段语义变） | 中 |
| 指法引擎 | 导出 JSON 的 finger | demo 动画观感（无需改码） | 低 |
| Motion IR 类型 | `motion.ts` + 双端校验 | demo `motionAdapter.ts` + golden 用例 | **高** |
| 键盘语义 | `layout.ts` + 文档 | 仅主项目自身；SightReading 无关 | 低 |
| 数据包 schema | CLI + 运行时加载 | 无（demo 不读包） | 中 |
| demo `Pianist` | 仅 demo | 无 | 低 |

## 7. 演进路线（按触发条件，不按时间）

| 阶段 | 目标 | 具体动作 | 触发条件 |
|------|------|---------|---------|
| **P0（已完成）** | 契约打通 | Motion IR v1 + `export:demo` + 首曲《欢乐颂》L2 | — |
| **P1（已完成，2026-10-23）** | 从「演示」到「教学」 | ① 导出前强制 `annotateScore(fill-gaps)`，`finger=0` 硬失败；② demo 自建 Web Audio 合成（双手增益 + 静音）；③ 音符轨道/音名与 clock 同步、可点击 seek；④ A–B 循环；⑤ 单手/静音 + 演示编配标注 | 曲库首批曲目过 QA |

| R4 | **时间驱动 ≠ 物理因果** | 琴键下沉由 `updatePressed(t)` 驱动，指尖目标独立解算 | 特写机位下理论可能指尖/键面不一致 | P1 特写验收；必要时让键沉跟随指尖 y |
| R5 | **包体膨胀** | three.js 若进主包，gzip 约 +150–200 KB | 首屏变慢 | 维持「demo 独立部署 + iframe/独立页」方案 |
